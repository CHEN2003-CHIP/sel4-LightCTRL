## 1. 编写目的

本文用于说明 LightDemo 项目的开发目标、任务分解、阶段计划、人员角色、交付物、验证计划和风险控制。文档面向项目成员、指导教师和课程检查人员，用于展示项目从需求到验证的工程管理过程。

## 2. 项目目标

项目目标是在 seL4/Microkit 环境下完成一个工程化汽车车灯控制样板系统，具备以下能力：

- 多 protection domain 组件化设计。
- UART 输入到 GPIO 输出的完整控制链路。
- 车辆状态参与控制策略。
- 集中式 fault lifecycle 和 fault mode 管理。
- 显式接口契约校验。
- host-side 单元测试和 QEMU 自动化验证。
- 可复查的测试结果目录和项目文档体系。

## 3. 项目范围

### 3.1 范围内

- `commandin` 输入网关。
- `vehicle_state` 车辆状态模块。
- `scheduler` 策略裁决模块。
- `lightctl` 执行协调模块。
- `gpio` 输出模块。
- `fault_mg` 故障管理模块。
- `light_contract` 接口契约模块。
- Makefile 构建和测试入口。
- QEMU smoke、fault integration、serial E2E 测试脚本。
- 软件工程汇报文档。

### 3.2 范围外

- 真实车载硬件接入。
- 真实汽车总线协议。
- 真实板卡 GPIO 电气验证。
- 汽车功能安全认证。
- 图形化用户界面。
- 数据库存储系统。

## 5. 阶段计划

| 阶段 | 工作内容 | 完成标准 |
| --- | --- | --- |
| 阶段 1：基础运行 | 建立 Microkit 系统描述和基础构建 | `make build` 生成 `loader.img` |
| 阶段 2：主链路实现 | 完成 UART 到 GPIO 的控制路径 | `make smoke` 通过 |
| 阶段 3：故障治理 | 完成 fault mode、lifecycle、recovery | `make test-fault` 通过 |
| 阶段 4：工程化增强 | 增加 contract、统一日志、测试证据目录 | `make test-contract` 通过 |
| 阶段 5：端到端验证 | 完成 smoke、fault、serial E2E | `make qemu-test` 通过 |
| 阶段 6：文档交付 | 补齐软件工程文档 | 汇报文档目录完整 |

## 8. 配置管理计划

项目配置项包括：

- 源码文件：`src/**/*.c`
- 头文件：`include/*.h`
- 系统描述：`systems/light.system`
- 构建脚本：`Makefile`
- 测试脚本：`scripts/*.sh`
- 单元测试：`tests/*.c`
- 工程文档：`docs/*.md`, `project-docs/*.md`, `reports/*.md`
- 验证证据：`test-results/<run-id>/`

构建产物 `build/`、`build-test-hooks/` 不作为源码设计依据，也不提交到版本库；最终测试证据可按 run id 归档为汇报和验证记录。

## 9. 质量保证计划

质量保证措施包括：

- 使用 `-Wall -Werror` 编译选项。
- 使用 `make test` 运行 host-side 测试。
- 使用 `make qemu-test` 运行 QEMU 自动化测试。
- 使用 `make test-contract` 验证接口契约。
- 保存 `test-results/<run-id>/` 作为回归证据。
- 通过需求-设计-实现-测试追踪矩阵检查覆盖关系。

## 12. 风险与应对

| 风险 | 应对措施 |
| --- | --- |
| 环境差异导致无法运行 | 固定 Ubuntu 22.04 + SDK 2.0.1 + QEMU 环境。 |
| 接口改动破坏通信 | 使用 `light_contract` 和 `make test-contract`。 |
| QEMU 日志不稳定 | 使用脚本匹配关键结构化日志。 |
| 故障恢复逻辑难以解释 | 使用 safety case 和状态机单测说明。 |
| 文档与实现不一致 | 使用追踪矩阵和验证报告收口。 |
