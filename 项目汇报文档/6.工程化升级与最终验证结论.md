# 工程化升级与最终验证结论

**项目名称：** 基于 seL4 + Microkit 的汽车车灯控制系统  
**文档类型：** 工程化升级总结  
**运行平台：** Ubuntu 22.04 + Microkit SDK 2.0.1 + QEMU `qemu_virt_aarch64`  
**验证证据目录：** `test-results/report-v3/`

## 1. 工程化成熟度评估

当前版本已经不再只是“能运行的 demo”，而是具备工程实践项目所需的基本闭环：

- 有明确的 protection domain 职责边界。
- 有集中管理的 Microkit channel ID 和 shared memory layout version。
- 有统一 transport message 结构和显式 contract 校验。
- 有 fault lifecycle、fault mode、恢复观察窗口和 anti-flap 机制。
- 有 host-side 单元测试和 QEMU 端到端测试。
- 有可保存、可复查的测试结果目录 `test-results/<run-id>/`。
- 有需求、架构、安全、测试、追踪矩阵和验证报告文档。

因此，本项目可以作为“基于 seL4/Microkit 的小型嵌入式控制系统工程样板”进行汇报，而不是只作为教程练习展示。

## 2. 技术亮点

### 2.1 多保护域隔离架构

系统将输入、裁决、执行、GPIO 输出、故障管理和车辆状态拆分为多个 Microkit protection domain：

```text
commandin -> scheduler -> lightctl -> gpio
commandin -> vehicle_state -> scheduler
lightctl / commandin -> fault_mg -> scheduler / gpio
```

这种结构体现了 seL4/Microkit 的隔离思想：不同职责由不同保护域承担，跨域通信通过显式 channel 和 shared memory 完成。

### 2.2 显式接口契约

新增 `light_contract.c` 和 `include/light_contract.h`，将原来隐含在代码中的工程约束显式化：

| 契约 | 内容 | 验证 |
| --- | --- | --- |
| Shared memory contract | `LIGHT_SHARED_STATE_LAYOUT_V3` 和 fault snapshot 边界 | `make test-contract` |
| Transport contract | version、type、payload length | `make test-contract` |
| Fault snapshot contract | mode、lifecycle、recovery tick、active mask | `make test-contract` |
| Channel contract | 已知 Microkit endpoint ID 表 | `make test-contract` |

运行时日志中可看到 `SCHED_CONTRACT`、`LIGHTCTL_CONTRACT`、`FAULTMG_CONTRACT` 和 `STATUS_SNAPSHOT ... contract=OK`。

### 2.3 集中式故障治理

`fault_mg` 是 fault mode 和 fault lifecycle 的唯一 owner。其他组件只能上报 fault 或请求 clear，不能直接修改全局故障状态。

当前故障治理能力包括：

- `NORMAL`
- `WARN`
- `DEGRADED`
- `SAFE_MODE`
- `ACTIVE`
- `RECOVERING`
- `STABLE`
- clear 后不直接恢复正常
- recovery tick 逐级降级
- 恢复期间再次故障会打断恢复

这使系统具备可解释的安全降级和恢复路径。

### 2.4 可观测和可回归验证

系统通过结构化日志输出关键证据：

- `CMD_MSG`
- `SCHED_TARGET`
- `LIGHTCTL_TARGET_SUMMARY`
- `GPIO_OUTPUT_SUMMARY`
- `FAULTMG_MODE_TRANSITION`
- `FAULTMG_CLEAR`
- `FAULTMG_RECOVERY_TICK`
- `STATUS_SNAPSHOT`

测试运行结果保存到 `test-results/<run-id>/`，便于汇报、复查和问题定位。

## 4. 关键日志证据

`test-results/report-v3/serial-e2e/qemu.log` 中包含：

```text
STATUS_SNAPSHOT fault=SAFE_MODE lifecycle=ACTIVE ... layout=3 contract=OK
STATUS_SNAPSHOT fault=SAFE_MODE lifecycle=RECOVERING ... layout=3 contract=OK
STATUS_SNAPSHOT fault=DEGRADED lifecycle=RECOVERING ... layout=3 contract=OK
```

这些日志证明：

- 两次 hardware-state error 后进入 `SAFE_MODE`。
- clear 后进入 `RECOVERING`，不会直接回到 `NORMAL`。
- recovery tick 使故障等级逐级下降。
- shared memory layout 和 runtime contract 在串口快照中可见。

## 5. 已关闭的问题

工程化改造过程中，曾发现 `commandin` 在处理 `?` 状态查询时发生 VMFault。该问题暴露出嵌入式 protection domain 中不应在关键运行路径中过度依赖复杂格式化路径。

修复方式：

- `commandin` 查询路径改为直接逐字段读取 shared memory 并输出。
- 保留 `layout=` 和 `contract=` 证据字段。
- 通过 `report-v3` 中的 `test-serial-e2e` 完成回归验证。

这体现了工程实践中的问题定位、修复和回归闭环。

## 6. 剩余限制

当前版本仍有以下边界：

- 验证环境是 QEMU，不是真实车载硬件。
- GPIO 行为通过日志和模拟 MMIO 观察。
- recovery window 使用 observation tick，不是真实时间源。
- fault taxonomy 和阈值是课程项目策略，不构成汽车功能安全认证结论。

## 7. 汇报结论

本项目已经形成了较完整的嵌入式工程实践闭环：

```text
需求 -> 架构 -> 接口契约 -> 安全降级 -> 自动化测试 -> 日志证据 -> 回归验证
```

相比普通 demo，本项目的工程性主要体现在：

- 隔离架构清晰
- 通信契约显式
- 故障治理集中
- 降级恢复可解释
- 测试证据可保存
- 文档追踪闭环完整

因此，当前版本适合作为成熟工程版进行课程汇报。
