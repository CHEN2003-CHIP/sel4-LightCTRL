# LightDemo 项目汇报文档使用说明

本文件夹用于替代参考项目中的 Word 汇报材料，内容已按本项目实际实现重写。当前提供 Markdown 版本，便于继续维护，也便于复制到网页端 GPT、WPS 或 Word 中生成最终 `.docx`。

## 文档清单

| 文件 | 对应参考文档 | 用途 |
| --- | --- | --- |
| `1.软件需求分析.md` | `1.软件需求分析.doc` | 说明项目背景、需求、功能需求、非功能需求、可行性和验收条件。 |
| `2.概要设计.md` | `2.概要设计.doc` | 说明系统总体架构、保护域划分、通信关系、共享内存和测试设计。 |
| `3.详细设计说明书.md` | `3.详细设计说明书.docx` | 说明各模块内部设计、核心数据结构、fault lifecycle、算法和接口细节。 |
| `4.用户使用手册.md` | `4.用户使用手册.doc` | 面向使用者说明环境准备、构建、运行、串口操作和故障验证流程。 |
| `5.需求-设计-实现-测试追踪矩阵.md` | 工程化补充材料 | 将需求编号映射到设计、实现文件和验证命令，形成检查闭环。 |
| `6.工程化升级与最终验证结论.md` | 工程化补充材料 | 汇总 LightDemo Engineering Baseline v1.0、技术亮点、当前边界和后续路线。 |
| `7.可行性研究报告.md` | 标准软件工程文档 | 说明技术、经济、运行、进度和风险可行性。 |
| `8.项目开发计划.md` | 标准软件工程文档 | 说明阶段计划、任务分解、质量保证和交付物。 |
| `9.数据库设计说明书.md` | 标准软件工程文档 | 说明本项目不使用传统数据库，并补充运行期数据结构设计。 |
| `10.测试报告.md` | 标准软件工程文档 | 记录 `report-v6` 测试环境、测试结果、缺陷回归和剩余风险。 |
| `11.标准软件工程文档清单.md` | 工程化补充材料 | 对照软件工程专业常见文档要求，说明当前文档齐备情况。 |

此外，`../docs/release_baseline.md` 是当前 release baseline 的单一入口，`../docs/engineering_roadmap.md` 是后续版本路线入口。

## 需要你最终替换的信息

文档封面中的以下字段使用了占位符，请在生成 Word 前按实际情况修改：

- 项目成员
- 班级 / 学号
- 指导老师
- 提交日期

## 推荐生成 Word 的方式

1. 将每个 Markdown 文件复制到网页端 GPT 或文档生成工具中。
2. 要求其“保持标题层级、表格、代码块、Mermaid 图，并生成适合工程实践提交的 Word 文档”。
3. 在 Word / WPS 中更新目录、页眉页脚和页码。

如果使用 Pandoc，也可以参考：

```bash
pandoc 1.软件需求分析.md -o 1.软件需求分析.docx
pandoc 2.概要设计.md -o 2.概要设计.docx
pandoc 3.详细设计说明书.md -o 3.详细设计说明书.docx
pandoc 4.用户使用手册.md -o 4.用户使用手册.docx
```

## 当前项目验证状态

截至本轮整理，当前 release baseline 为 **LightDemo Engineering Baseline v1.0**，对应验证运行编号 `report-v6`。项目在 Ubuntu 22.04 虚拟机中已验证：

```bash
make test TEST_RUN_ID=report-v6
make build
make qemu-test TEST_RUN_ID=report-v6
make evidence TEST_RUN_ID=report-v6
```

其中 `make qemu-test` 已包含：

- `make smoke`
- `make test-integration-fault`
- `make test-serial-e2e`

三项均已通过。

测试证据目录：

```text
test-results/report-v6/
```

当前工程边界和后续路线已经在 `6.工程化升级与最终验证结论.md`、`../docs/release_baseline.md` 和 `../docs/engineering_roadmap.md` 中同步说明。

## 建议汇报讲解顺序

1. 先用 `2.概要设计.md` 讲总体架构和保护域拆分。
2. 再用 `5.需求-设计-实现-测试追踪矩阵.md` 说明工程闭环。
3. 用 `3.详细设计说明书.md` 展开 fault lifecycle 和 channel/shared memory 细节。
4. 用 `10.测试报告.md` 展示 `report-v6` 的 host-side 与 QEMU 验证证据。
5. 最后用 `6.工程化升级与最终验证结论.md` 收束到当前边界、release baseline 和后续路线。
